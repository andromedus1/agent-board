# Session Domain Contract

## Brief

Define the strict TypeScript and runtime-validated contract for Agent Board
session identity, terminal presence, normalized agent state, observation
evidence, revisions, and stable error codes. Expose the ports needed by storage,
clock, terminal, and agent-event adapters without importing concrete processes
or filesystem behavior.

Acceptance requires invalid records and unsafe labels to fail explicitly,
orthogonal state dimensions to remain independently writable, and clean process
exit to remain evidence rather than a health value.

## Inherited design decisions

- The parent epic's canonical schema, no-compatibility, adapter-boundary, and
  projection ownership decisions are fixed inputs.

## Design decisions

- Zod schemas are the runtime source of truth and TypeScript types are inferred
  from them. Hand-maintained interfaces would create two contracts.
- External records use strict objects and explicit enums; unknown fields fail at
  the canonical store boundary until a real external compatibility obligation
  exists.
- Project labels accept normal Unicode but reject empty/whitespace-only values,
  C0/C1 controls, line separators, and terminal escape bytes.
- Session IDs are opaque non-empty strings generated by the application layer;
  Ghostty and Codex identifiers remain typed values, not identity aliases.

## Architectural choice

Considered plain TypeScript types with handwritten validators, JSON Schema plus
generated types, and Zod-first schemas. Plain types are smallest initially but
duplicate validation logic. JSON Schema generation is useful for a public wire
contract but adds build machinery before one exists. Zod-first is the selected
shape because all current boundaries are local and TypeScript-native while still
requiring runtime validation.

The domain package stays functional: schemas, type aliases, small validation
helpers, and port interfaces. It does not construct concrete adapters or own
process lifecycle.

### Unit 3: Canonical session schemas

**File**: `src/domain/session.ts`

```typescript
export const SCHEMA_VERSION: 1;
export const ProjectLabelSchema: z.ZodType<string>;
export const ObservationSchema: z.ZodObject<{
  observedAt: z.ZodString;
  evidenceKind: z.ZodString;
  confidence: z.ZodEnum<["authoritative", "corroborated", "inferred"]>;
  detail: z.ZodOptional<z.ZodString>;
}>;
export const SessionRecordSchema: z.ZodType<SessionRecord>;
export type SessionRecord = z.infer<typeof SessionRecordSchema>;
export function parseSessionRecord(input: unknown): SessionRecord;
export function parseProjectLabel(input: unknown): string;
```

The strict record includes `schemaVersion`, `revision`, `sessionId`, `identity`,
`terminal`, and `agent` exactly as locked in architecture. Timestamps are
RFC3339 strings and revisions are non-negative safe integers.

**Acceptance Criteria**:

- [ ] Clean process exit cannot be represented as a health enum value.
- [ ] Terminal presence and agent health are independent validated dimensions.
- [ ] Unsupported schema versions and unsafe labels return typed domain errors.

## Implementation Order

1. Package scaffold and registries establish compilation and shared constants.
2. Errors and schemas establish the runtime contract.
3. Ports depend only on those domain types.
4. Contract tests lock behavior before adapters consume it.

## Testing

Use `node:test` and `node:assert/strict` through `tsx --test`. Favor table-driven
schema boundary tests; do not snapshot Zod internals or implementation details.

## Risks

- **Zod generic complexity**: spelling every concrete Zod object generic can make
  declarations brittle. Export inferred public types and concrete schema values,
  avoiding unnecessary explicit schema generics. Fallback: simplify signatures
  while keeping runtime behavior unchanged.
- **Over-validation of labels**: rejecting ordinary Unicode would undermine the
  naming workflow. Reject only terminal/script-dangerous controls and blank input;
  integration adapters still pass values as positional arguments.

## Child stories

None. The units share one small foundational type surface and fit a single
implementation stride; splitting them would create handoff overhead.
