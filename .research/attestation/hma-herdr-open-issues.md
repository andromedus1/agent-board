## Summary

State of the named defects and of newer open p1 issues in herdrdev/herdr as of 2026-11-10, read with `gh`. #5170, #5471 and #4391 remain open and unresolved; no open p0 issue exists. New open p1 issues include a macOS remote output stall (#5624), a second-client stall on a shared Claude Code tab (#5749), saved-machine SSH probes tripping OpenSSH PerSourcePenalties (#5634), and session-resume identity bugs for Codex and Claude (#5837, #5909). Issue bodies are reporter accounts; causes are reporter hypotheses unless a maintainer comment says otherwise.

## Key passages

- [1] #5170 "Linux herdr --remote: dropping the local SSH client kills all remote pane processes": OPEN; labels maintainer-needed, p1, linux, remote, sessions, triaged; updated 2026-10-11; one comment from collaborator ogulcancelik: could not reproduce "over tailscale ssh with KillUserProcesses=false"; asks for `loginctl show-user $USER -p KillUserProcesses` output. No reporter reply is in the thread. The body (reporter account, Linux server): `herdr --remote` "starts a remote server that dies when the local client or SSH session drops. Every pane process is killed"; reconnecting "starts a new server and restores the layout; agents come back as new processes (or empty shells)"; the reporter observes the server sits in the SSH logind session scope. Linux-labelled.
- [2] #5471 "Server memory grows without bound while a TUI client is connected but stops reading": OPEN; labels bug, maintainer-needed, p1, linux, remote, performance, triaged; updated 2026-11-01. A second reporter (2026-11-01) reproduced on stable 0.9.3: "about 25 panes with 16 Claude Code sessions", server reached 8.3 GB RSS after 27 days and never shrank; the reporter attaches with `herdr --remote` over SSH from a laptop that sleeps, and "the remote-client-bridge on the server stays connected until sshd drops the session (ClientAliveInterval 300, ClientAliveCountMax 2, so up to 10 minutes per sleep). Shortening that to 90 seconds is our mitigation for now." The first-report body, re-read 2026-11-10, says the server grows "about 4 MB per minute as long as such a client is attached, and never levels off", versus RSS levelling at 60 to 90 MB with no stalled client, and a restart brought a 16 GB process "back to 24 MB"; it also states that a TUI attached over SSH from a laptop that goes to sleep behaves the same way. Linux-labelled.
- [3] #4391 "Detaching a working --remote session (Prefix+q) on macOS prints ConnectionReset and leaves the terminal unrestored": OPEN; labels bug, maintainer-needed, p2, macos, remote, sessions, triaged; updated 2026-10-27. A commenter reproduced on Linux to Linux with herdr 0.9.5: "Session detaches and persists correctly; only the client exit prints `Error: Os { code: 104, kind: ConnectionReset }`", with server and client logs clean, "purely the client's exit path".
- [4] #5624 "macOS remote: server -> client stream stalls silently; panes freeze until the remote-client-bridge ssh is killed": OPEN, p1, macos, remote; client 0.9.5 (macOS) to saved-machine server 0.9.5 (macOS); input still reaches the remote but the client does not repaint, "does not recover on its own"; occurred twice in two days; workaround: kill the client's `ssh ... remote-client-bridge` child, after which "remote panes survive"; a commenter measured 4 of 6 stalls within about a minute of switching machines.
- [5] #5749 "Second attached client stalls when it views the same tab as another client and that tab runs Claude Code": OPEN, p1, macos, input, rendering; herdr 0.9.5, macOS 26.5 Apple silicon, iTerm2; the second client "becomes unusable for a minute or more" while the first stays responsive; a plain-shell tab is responsive.
- [6] #5634 "Saved-machine SSH probes trip OpenSSH 10 PerSourcePenalties and lock the client out of the host": OPEN, p1, macos, linux, remote; with OpenSSH 9.8+ on the host, bursts of parallel probes closing before authentication caused a "penalty of 16 seconds" that blocks all SSH from the client address, including interactive ssh.
- [7] #5905 "Herdr panes run outside the user launchd session: system DNS fails (curl, gh) and notifyd is unreachable": OPEN, p1, macos, sessions; created 2026-11-09; reporter on the Herdr desktop app 0.9.1 where panes are children of `herdr-core` started via launchd; a commenter's control result: "the Herdr CLI does not have this problem" (CLI chain `herdr server` under Ghostty, `launchctl managername` = Background). The affected path is the desktop app, not the TUI.
- [8] #5784 "macOS: GUI apps spawned from a Herdr-held terminal abort in TransformProcessType": OPEN, p1, macos, sessions; component stated as `herdr-core` on macOS.
- [9] #5837 "Codex pane's agent_session becomes its auto-review subagent thread, replacing the pane's real conversation": OPEN, p1, macos, sessions, integrations; reporter states `session.json` persists a swapped pair so resume would target the wrong thread. #5909 "Claude Code: after /branch, a Herdr restart brings back the conversation from before the branch": OPEN, p1, linux, sessions, integrations. #5921 "OpenCode panes restore to a new chat after a cold Herdr restart": OPEN, p1, macos, sessions.
- [10] `gh issue list --label p0 --state open` returned no issues; the open p1 list contains the issues above plus Windows-labelled items not relevant to a macOS host.
