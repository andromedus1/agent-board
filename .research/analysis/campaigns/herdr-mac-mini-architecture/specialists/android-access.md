# Android access (facet `android-access`)

Facet of the `herdr-mac-mini-architecture` campaign. Sources fetched 2026-11-10. Most Moshi evidence is vendor documentation or vendor-authored articles; nothing here was run on an Android device. Existing `rps-blink-tailscale-mosh` and `rps-tailscale-ssh-kb` are reused after a currency check (the cited passages are still on the live pages); every other source is a new `hma-android-*` attestation.

## 1. Moshi on Android

**Released, not beta.** Moshi has a Google Play listing, "Moshi: tmux/herdr SSH terminal" by Moshi Tech Limited, rated 4.7 from 340 reviews, "10K+" downloads, updated Nov 9, 2026, with in-app purchases [hma-android-moshi-play-listing]{1}. The version string 4.3.2 sits beside the What's new text in the page data [hma-android-moshi-play-listing]{2} (read from embedded data, not a visible label). Requirement: "Android 10 or newer" [hma-android-moshi-docs-install]{1}. The listing's own feature text names Mosh, tmux/Zellij/herdr pairing with auto-reattach, an approve/deny/answer inbox, push, and webhooks [hma-android-moshi-play-listing]{3}[hma-android-moshi-play-listing]{4}.

**Parity with iOS.** The vendor states the iOS-only items: Live Activities, Dynamic Island and the Apple Watch companion; on Android "you still get the terminal, Agents feed, push, and host-side hooks" [hma-android-moshi-article-android]{2}. The docs repeat that Apple Watch is iOS only [hma-android-moshi-docs-subscription]{3}. Everything else in the feature list (SSH, Mosh, multiplexer pairing, Sidebar, Chat View, inbox) is documented without a platform split; the product docs are worded for iOS (iPhone, iPad, Keychain) and have no Android page [hma-android-moshi-docs-tailscale]{1}[hma-android-moshi-docs-e2ee]{4}. So Android parity is vendor-asserted by omission, not by an explicit parity statement {inferred: absence of a stated split, plus the article's explicit iOS-only list}.

**Labels and aggregated states on the phone.** The Sidebar Workspaces view lists Herdr workspaces and their tabs fetched live, and long-press Rename renames a workspace, tab or pane on the host [hma-android-moshi-docs-sidebar]{1}[hma-android-moshi-docs-sidebar]{4}. The Agents view groups agents as Waiting, Done, Working and Idle, sorted by time in state, but agent rows are named after the agent's conversation or a name the user gives in Moshi, unless "Use tab names" is on [hma-android-moshi-docs-sidebar]{2}[hma-android-moshi-docs-sidebar]{7}. The Inbox is a Needs you / Working / Done board, one row per session, each row naming machine, project and model [hma-android-moshi-docs-agents-inbox]{1}[hma-android-moshi-docs-agents-inbox]{3}. How the Inbox "project" value is derived is not documented; the privacy section lists "project name" as event metadata [hma-android-moshi-docs-hooks]{6}. A per-session `project: feature` string is therefore reliably visible only if it is the Herdr workspace/tab label {inferred: from the Sidebar tree showing host names and "Use tab names"}. Moshi's Sidebar status for Herdr comes from "Herdr's own agent awareness" [hma-android-moshi-docs-multiplexer]{4}, while the Agents view says "Agent status comes from the agents' hooks" [hma-android-moshi-docs-sidebar]{5}; neither page shows a native-versus-inferred confidence marker in the UI {inferred: no such marker is described}. The Inbox board is framed around iPhone, iPad and Apple Watch [hma-android-moshi-docs-agents-inbox]{6}; its Android layout is undocumented.

**Notification noise controls.** Pushes are silent for agents running outside tmux/Herdr by default, nested-agent events are delivered by default, and macOS hosts can silence visible pushes while the console is unlocked [hma-android-moshi-docs-hook-settings]{1}[hma-android-moshi-docs-hook-settings]{2}[hma-android-moshi-docs-push]{3}. The inbox keeps one active row per session [hma-android-moshi-docs-hooks]{5}. Completed turns stay active for 10 minutes and everything archives after 6 hours [hma-android-moshi-docs-agents-inbox]{4}.

**Data flow.** Terminal traffic and transcripts stay host-to-phone; Moshi's server receives event summaries, up to 256 characters of the command behind an approval, project name, session ID, tool name and approval decisions [hma-android-moshi-docs-hooks]{6}. E2EE is off by default and, when on, makes the host ignore any approve/deny not sealed with its key [hma-android-moshi-docs-e2ee]{1}[hma-android-moshi-docs-e2ee]{2}. The Play data-safety panel says no data collected or shared (developer-declared) [hma-android-moshi-play-listing]{6}.

## 2. Approval semantics

**Documented carriage is keystrokes into the pane, gated by a re-check.** "Tapping Approve or Deny on a pending agent action injects the right keys into the exact pane, after moshi-hook has re-captured the screen and verified the prompt is still the one you saw" [hma-android-moshi-docs-multiplexer]{2}. Chat View's buttons "act on the live session; they do not approve a copied or server-side request", and each agent exposes permissions differently, so some cards say to answer in the terminal [hma-android-moshi-docs-chat-view]{3}[hma-android-moshi-docs-chat-view]{4}. Answering on the host clears the pending item on the phone [hma-android-moshi-docs-multiplexer]{3}. The pages read do not state per-agent mechanics (Claude versus Codex) in the approval row and do not say Moshi uses the agents' structured permission hooks; the exact event list `moshi-hook install` writes into `~/.claude/settings.json` and `~/.codex/hooks.json` is not enumerated [hma-android-moshi-docs-hooks]{4}.

Both agents offer a structured alternative that Moshi's docs do not claim to use: Claude Code's PermissionRequest hook returns `decision.behavior` allow or deny [hma-android-claude-code-hooks-docs]{1}; Codex's PermissionRequest hook "can allow the request, deny the request, or decline to decide" [hma-android-codex-hooks-docs]{1}.

**Guardrail reading** {inferred: against the Agent Board rule that a generic keystroke must not stand for semantic approval}. A button tap that becomes injected keys is a keystroke carriage with a screen re-verification control, not a structured decision bound to a request ID. Two further points: the free tier allows 5 inbox actions before Pro [hma-android-moshi-docs-subscription]{1}; and with E2EE on, each decision is sealed "to one specific approval" [hma-android-moshi-docs-e2ee]{2}, a binding the default configuration lacks.

**Known attribution defect for Codex.** Codex 0.157 turned `features.daemon_auto_start` on by default; interactive sessions then share one background server and Moshi "attributes every Codex session to that first terminal", so "replies and inbox approvals go to the wrong pane" until `moshi-hook doctor --yes` turns it off [hma-android-moshi-docs-troubleshooting]{3}. Install asks before changing the setting [hma-android-moshi-docs-hooks]{4}. This bears directly on a fleet of 5 to 15 Codex sessions.

## 3. Mosh, Tailscale and Herdr

**Moshi versus Blink on mosh after Tailscale SSH.** Moshi docs: with Tailscale SSH on, "Tailscale grabs port 22 for every tailnet connection", key auth stalls ~60 s, and "mosh cannot bootstrap through Tailscale SSH because it is not real OpenSSH"; the recommended path is `sudo tailscale set --ssh=false` [hma-android-moshi-docs-tailscale]{3}[hma-android-moshi-docs-tailscale]{4}. Blink docs: advertise `tailscale up --ssh`, `ssh` with tailnet identity, then `mosh --install-static` to install mosh-server, then `mosh` [rps-blink-tailscale-mosh]{1}[rps-blink-tailscale-mosh]{2}[rps-blink-tailscale-mosh]{3}. A Moshi article adds a third position: keep Tailscale SSH and also enable OpenSSH, "Both can coexist", with mosh bootstrapping through OpenSSH [hma-android-moshi-article-mosh-failed]{2}. These are recorded in Contradictions; none is adjudicated here. A fact that narrows the macOS case: Tailscale's KB says Tailscale SSH takes over port 22 for tailnet traffic and on macOS works only with the open-source `tailscale`/`tailscaled` CLI variant [rps-tailscale-ssh-kb]{1}[rps-tailscale-ssh-kb]{2}; whether the operator's Mac mini runs that variant belongs to the host facet.

**mosh-server on macOS.** Needs: `brew install mosh` [hma-android-moshi-docs-install]{3}; macOS Remote Login on even over Tailscale [hma-android-moshi-docs-tailscale]{2}; mosh-server on the non-interactive SSH PATH, because Homebrew's `~/.zprofile` guidance is not read by the bootstrap shell, so add the `brew shellenv` line to `~/.zshenv` or set an absolute Mosh path in Moshi [hma-android-moshi-article-mosh-macos-path]{1}[hma-android-moshi-article-mosh-macos-path]{2}[hma-android-moshi-docs-troubleshooting]{1}. In Auto mode a missing mosh-server silently falls back to SSH; the terminal badge shows Mosh or SSH [hma-android-moshi-article-mosh-macos-path]{3}. UDP: mosh uses UDP 60000–61000 and the vendor says over Tailscale "no port rules needed" [hma-android-moshi-article-mosh-failed]{3}. A UTF-8 locale is required and shell startup files must print nothing in non-interactive shells [hma-android-moshi-article-mosh-failed]{4}. macOS Application Firewall handling is not covered in the pages read. Closed-lid or sleeping Macs: UDP does not keep macOS awake; Moshi sends a wake-up probe on a new mosh connection [hma-android-moshi-docs-tailscale]{6} (host facet owns sleep policy).

**Herdr and mosh.** Herdr's `--remote` mosh request (#1779) was closed NOT_PLANNED seven seconds after creation by a bot citing the bug-report template, so there is no maintainer decision on mosh [hma-android-herdr-issue-1779]{1}[hma-android-herdr-issue-1779]{3}. Herdr's docs for phones say "any SSH client", that the TUI adapts to narrow screens, and name moshi for iPhone; mosh transport is not mentioned and Android is not mentioned [hma-android-herdr-docs-how-to-work]{1}[hma-android-herdr-docs-how-to-work]{2}[hma-android-herdr-docs-how-to-work]{3}. Running Herdr inside a mosh session is the path Moshi uses, and open or closed Herdr issues show friction there: 24-bit colour makes the UI unreadable on a Mosh client with an older library (open) [hma-android-herdr-issue-5768]{1}[hma-android-herdr-issue-5768]{2}; a mosh attach altered other clients' panes (closed NOT_PLANNED) [hma-android-herdr-issues-mosh-list]{3}; a phone navigator clipping report over Moshi was closed stale [hma-android-herdr-issue-3840]{1}[hma-android-herdr-issue-3840]{4}. Those reports are iOS or Termius; no Android-specific Herdr report was found.

**Is plain SSH over Tailscale enough on cellular?** Not settled by the sources. The Herdr server and panes persist on the Mac regardless of the client [hma-android-herdr-issue-1779]{2}, so a dropped SSH client costs a reattach, not the work. Moshi's own framing is that SSH "works anywhere TCP SSH works" and mosh is "the better choice for mobile use when UDP is available" [hma-android-moshi-docs-terminal-sessions]{1}. Moshi's vendor article says SSH alone freezes when the radio changes [hma-android-moshi-article-android]{7} (vendor claim). Auto-reattach to the Herdr session after an app kill is Pro and documented generally for reconnects [hma-android-moshi-docs-terminal-sessions]{3}. Tailscale's own roaming behaviour on Android was not documented in the pages read.

## 5. Android notification mechanics available in this topology

- **moshi-hook push**: from the Mac to Moshi's push service to the app [hma-android-moshi-docs-hooks]{6}; webhooks via `api.getmoshi.app/api/webhook` with tap-to-open `moshi://herdr?workspace=` links [hma-android-moshi-docs-push]{2}; the daemon on the Mac needs only outbound HTTPS to Moshi, so event delivery does not depend on the phone reaching the tailnet [hma-android-moshi-docs-hooks]{10} {inferred: from the outbound-only statement and the push path in the privacy section}.
- **ntfy**: Android app from Google Play, F-Droid or GitHub; instant delivery uses a foreground service so messages arrive in doze, otherwise they can be delayed "many minutes, or even hours"; Firebase is used only for ntfy.sh on the Play flavor, not for self-hosted servers [hma-android-ntfy-phone-docs]{2}[hma-android-ntfy-phone-docs]{3}. A self-hosted ntfy server could sit on the tailnet {extends: placement on the tailnet is not stated in the page}.
- **Pushover**: priority 1 "bypass[es] a user's quiet hours"; a receipt/callback API is listed for emergency priority [hma-android-pushover-api]{1}.
- **Claude Code**: the Notification hook fires for `permission_prompt`, `idle_prompt`, `agent_needs_input` and `agent_completed` and is for side effects only [hma-android-claude-code-hooks-docs]{2}; a script could post to ntfy or Pushover {extends}.
- **Codex**: `notify` runs an external program on `agent-turn-complete` only; the TUI's `approval-requested` filter produces terminal OSC 9 or BEL, not a phone push [hma-android-codex-config-advanced]{1}[hma-android-codex-config-advanced]{2}. Approval alerts for Codex would need its PermissionRequest hook [hma-android-codex-hooks-docs]{1} {extends}.
- **Native provider push**: Claude app push needs Remote Control active [hma-android-claude-remote-control-docs]{3}; Codex notifications need the ChatGPT desktop host [hma-android-codex-remote-connections-docs]{3}.
- **wherdr Web Push**: working-to-blocked and working-to-done events, suppressed while a conversation is open on any device [hma-android-wherdr-docs-notifications]{1}[hma-android-wherdr-docs-notifications]{4}.

## 6. Tailscale on Android (brief)

Tailscale's Android install page is a quickstart with no battery, always-on or coexistence guidance [hma-android-tailscale-changelog-android]{4}. Changelog entries mention improved VPN-service logic with Always-On VPN enabled and a persistent VPN status notification on Android [hma-android-tailscale-changelog-android]{1}[hma-android-tailscale-changelog-android]{2}; the "another VPN app is running" fixes are listed under macOS and iOS, not Android [hma-android-tailscale-changelog-android]{3}. Coexistence with other VPNs on Android and battery or background limits for Tailscale are therefore not documented in the pages read. Adjacent Android battery notes: Claude app push can be delayed by battery optimization [hma-android-claude-remote-control-docs]{3}, and ntfy needs a foreground service for doze-time delivery [hma-android-ntfy-phone-docs]{2}. Moshi says any OS-level VPN works transparently, in iOS wording [hma-android-moshi-docs-connections]{3}.

## Disconfirming analysis

- **"Moshi Android is at parity."** Searched the attested Moshi pages for platform splits. Found the explicit iOS-only list [hma-android-moshi-article-android]{2}, iOS-only Watch [hma-android-moshi-docs-subscription]{3}, an iOS-worded Keychain key store [hma-android-moshi-docs-e2ee]{4}, and no Android doc page (the `/docs/android` path returned 404 on fetch). A Play reviewer said approvals never worked and notifications persisted after VPN disconnect; the developer replied that approval failure is unexpected and that push does not ride the VPN [hma-android-moshi-play-listing]{8}. Outcome: parity stays vendor-asserted; Android approval delivery has one adverse anecdote and no independent test.
- **"Approvals are keystrokes."** Searched hooks, multiplexer, Chat View, Agents, hook-settings and troubleshooting pages for any statement that Moshi answers the agents' PermissionRequest hooks. None found. The install page lists managed config files but not hook events [hma-android-moshi-docs-hooks]{4}, so a structured path for some agent cannot be excluded {ambiguous: managed hook event list not enumerated}.
- **"Herdr does not recommend mosh."** Searched Herdr docs and issues. Docs name moshi for iPhone and say any SSH client works [hma-android-herdr-docs-how-to-work]{3}; the sole mosh transport request was closed by template bot, not on merits [hma-android-herdr-issue-1779]{3}. Outcome: Herdr is neutral-to-silent, not opposed; the mosh-related Herdr bugs are real but iOS-reported.
- **"Android is the weak spot for provider-native remote."** Both are available on Android: Claude app (Claude Code only) [hma-android-claude-remote-control-docs]{1} and the ChatGPT app for Codex [hma-android-codex-remote-connections-docs]{1}. Counter-evidence for using them with the Herdr topology: Codex requires the desktop app, not the CLI [hma-android-codex-remote-connections-docs]{2}; Claude requires one Remote Control session per interactive process unless server mode [hma-android-claude-remote-control-docs]{4}.
- **"JuiceSSH is dead."** Single source, the vendor's article [hma-android-moshi-article-android]{5}; not independently verified against Play.

## Contradictions

- **Mosh bootstrap through Tailscale SSH.** Moshi docs: mosh cannot bootstrap through Tailscale SSH; disable it for key auth [hma-android-moshi-docs-tailscale]{3}[hma-android-moshi-docs-tailscale]{4}. Blink docs: enable Tailscale SSH, then `mosh --install-static` and `mosh` [rps-blink-tailscale-mosh]{2}[rps-blink-tailscale-mosh]{3}. Relationship: contradicts within a shared frame (same host setup, different clients), possibly qualified by each client's bootstrap implementation {contested: not tested here}.
- **Moshi docs versus Moshi article on coexistence.** Docs: Tailscale SSH takes port 22 for every tailnet connection and bypasses sshd [hma-android-moshi-docs-tailscale]{3}. Article: keep Tailscale SSH and OpenSSH; "Both can coexist" [hma-android-moshi-article-mosh-failed]{2}. Tailscale's KB says it claims port 22 for tailnet traffic [rps-tailscale-ssh-kb]{1}. Relationship: tension.
- **ConnectBot mosh support.** Moshi article table: "No (SSH-oriented)" [hma-android-moshi-article-android]{6}; ConnectBot Play listing: "SSH & Mosh client" [hma-android-connectbot-play]{1}. Relationship: contradicts.
- **Moshi pricing.** Article: $7.99/mo, $69.99/yr [hma-android-moshi-article-android]{3}; pricing page: $9.99/mo, $89.99/yr [hma-android-moshi-pricing]{1}. Relationship: tension (dated sources; the pricing page is current).
- **Approvals working on Android.** Vendor: approvals reach every opted-in device including Android [hma-android-moshi-docs-licensing]{1}; one Play review (September 30, 2026): approvals did not work [hma-android-moshi-play-listing]{8}. Relationship: tension; unresolved.
- **Herdr phone suitability.** Herdr docs: the TUI adapts to narrow screens [hma-android-herdr-docs-how-to-work]{2}; a user report: navigator clips on a phone over Moshi, closed stale [hma-android-herdr-issue-3840]{3}. Relationship: tension.
