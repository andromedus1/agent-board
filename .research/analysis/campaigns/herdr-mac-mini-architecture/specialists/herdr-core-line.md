# Facet: the herdr-core line versus Herdr TUI

Scope: whether herdr-core (with or without the desktop Herdr app) plus the official Herdr mobile app is a better host runtime than Herdr TUI for an always-on headless Mac mini running 5-15 Claude Code and Codex sessions, reached over Tailscale from a MacBook Air and an Android phone. Everything below is vendor documentation or issue-tracker reporter accounts read on 2026-11-10; nothing was installed or run.

## Lane conclusion

The core line addresses a structural weakness of the TUI for this operator (screen-inferred status). Core takes status only from what the program reports, never from the screen [hma-core-readme]{6}, and both Claude Code and Codex are reported to emit OSC 7501 natively [hma-core-app-issue-537]{2} [hma-core-codex-osc7501-issues]{1}. It also has an official Android client [hma-core-play-herdr-listing]{1}. It is weaker on the operator's recovery and notification priorities: after a reboot kept terminals return as bare shells and no agent session is resumed [hma-core-site-mobile-privacy-faq]{6} [hma-core-issues-resume-recovery]{2}, and the only documented phone alert is an in-app banner while the app is open [hma-core-site-mobile-privacy-faq]{1}. It is also very young (see Q1) and its macOS hosting model for a headless, SSH-started core has open defects [hma-core-issues-macos-hosting]{1}. So it is a credible but not yet superior host: it wins on native state, loses on resume and closed-app alerts. {inferred: aggregate across the cited attestations}

## Q1. Versions, cadence, maturity, macOS install and headless service

- herdr-core is 0.1.x: tags v0.1.11 to v0.1.20, repository created 2026-10-16, Apache-2.0 [hma-core-readme]{8}. Releases 0.1.16 to 0.1.20 landed on 10-31, 11-02, 11-04, 11-07 and 11-10 [hma-core-changelog]{1}. The desktop app is at 0.1.15 (2026-11-10) [hma-core-app-readme]{8}. The API is "preview (protocol generation 1, version 0.x)" [hma-core-api-schema]{1}. Maturity is therefore weeks, with a release every two to three days.
- Standalone install on macOS needs no desktop app: `curl -fsSL https://releases.herdr.dev/core/install.sh | sh`, Apple silicon builds exist [hma-core-readme]{2}. On macOS the core is its own signed app bundle, Herdr Core.app, installed under `~/.local/share/herdr-core/active/` with `hc` linked into `~/.local/bin` [hma-core-docs-commands-skill]{7} [hma-core-changelog]{5}.
- Headless service: not documented. The CLI "starts a background core when it needs one" [hma-core-docs-security]{8}. `hc server start|stop|status|restart` exist, but no login-item or boot-service command appears in the command list read [hma-core-docs-commands-skill]{10}. On macOS "desktop starts use a one-shot launchd job" while "SSH starts stay direct" [hma-core-docs-commands-skill]{5}; a headless Mac mini reached by phone or laptop would use the SSH path. No page read states how the core behaves with no GUI login session or after a reboot before any client connects. {extends: the reboot-then-first-connect start path is inferred from #12's note that a saved connection's `hc connect` can start a core [hma-core-issues-macos-hosting]{2}}
- Defects on the SSH-started path (open at read time): #104 core started over SSH runs in a Background security session and Keychain password reads fail (`password_exit=36`), fixed only by restarting from the graphical session [hma-core-issues-macos-hosting]{1}; #203 programs get `PATH=/usr/bin:/bin:/usr/sbin:/sbin` plus `.zshenv`, so `codex` could not start [hma-core-issues-macos-hosting]{4}; #12 notes the same bare-PATH start from `sshd-session` [hma-core-issues-macos-hosting]{2}. These matter directly for a headless Mac mini whose only login is SSH.
- #5905 (desktop app, reporter on Herdr 0.9.1, herdr-core started via launchd, panes outside the user's launchd session, DNS via system resolver fails, notifyd unreachable) is open, p1, macos, created 2026-11-09; a commenter's control found "the Herdr CLI does not have this problem" [hma-herdr-open-issues]{7}. #5784 (GUI apps spawned from a Herdr-held terminal abort, component herdr-core on macOS) is open p1 [hma-herdr-open-issues]{8}; a comment on #5784 reports on macOS 27.0.1, herdr-core 0.1.18 that "the whole session goes down, not only Chrome" [hma-core-issues-macos-hosting]{7}. The 0.1.20 changelog fixes several adjacent macOS items: core starting separately from the app after login or reboot, new terminals working after logout/login, and the Dock background-entry kill [hma-core-changelog]{2} [hma-core-changelog]{3} [hma-core-changelog]{4}. Whether 0.1.20 closes #5905 is not stated in the sources read.
- p0/p1: `gh issue list --label p0` on herdrdev/herdr returned none [hma-herdr-open-issues]{10}. herdr-core and herdr-app define no p0/p1 labels at all [hma-core-readme]{8} [hma-core-app-readme]{9}, so there is no maintainer severity triage for the repositories that matter to this line. The 106 open core issues were not individually triaged here.

## Q2. Status for Claude Code and Codex under herdr-core

- Mechanism: core stores what the program reports through OSC 7501 (`idle`, `working`, `done`, `blocked`, `error`; `blocked` can carry `kind` permission, question or auth) and "does not guess from screen text or recognize agent brands" [hma-core-docs-commands-skill]{1} [hma-core-readme]{6}.
- Claude Code: native emission since 2.1.295, enabled only if the terminal answers a startup probe within about 2 s [hma-core-claude-code-osc7501-issues]{1}. A third party confirmed under hc: probe succeeds, `status: done` [hma-core-app-issue-537]{2}. Known gaps (all open, reporter accounts): a slow `--resume` start (about 9 s with a 1.1 MB transcript) leaves the session permanently unreported [hma-core-app-issue-537]{3}; a probe reply arriving after the DA1 sentinel disables status [hma-core-claude-code-osc7501-issues]{3}; backgrounding, agent view or session continuation stops reporting until `/exit` or `--resume` [hma-core-claude-code-osc7501-issues]{4} [hma-core-claude-code-osc7501-issues]{5}.
- Codex: emits `idle`/`working`/`done` with `app=codex` on every state change when stdout is a tty (seen on 0.165.0) [hma-core-codex-osc7501-issues]{1}. An end-of-turn edge case keeps `working` while background terminals run [hma-core-codex-osc7501-issues]{3}. Codex must be run with `--no-daemon` under hc or its commands execute outside hc [hma-core-docs-commands-skill]{8}. What `blocked` carries for a Codex approval is unmeasured in the source read [hma-core-cockpit-issue-59]{2}.
- Hooks: herdr-core does not install Claude or Codex hooks. The TUI's Claude hook (`herdr-agent-state.sh`) exits unless TUI env vars are set and only reports a session identity under the TUI, so it does nothing in core panes [hma-core-app-issue-537]{1}. Hook-to-state mapping (SessionStart/UserPromptSubmit/Stop/Notification/SessionEnd to idle/working/done/blocked/idle/clear) exists only as a third-party workaround [hma-core-app-issue-537]{6}.
- Failed state: `error` exists in the protocol and renders as "needs you" with `blocked` in the shared display rule [hma-core-app-docs-labels]{3}. Whether Claude Code or Codex actually emit `error` is not documented in the sources read; a Claude Code issue asks for the states to be documented because "today they can only be read from the code" [hma-core-claude-code-osc7501-issues]{7}.
- Fallback and provenance: none. "A program that does not report status has none" [hma-core-readme]{6}; a Claude that skipped the probe "stays invisible even though the screen clearly shows an idle Claude prompt" [hma-core-app-issue-537]{4}. Core stores records "as reported" with an `app` field naming the reporter [hma-core-api-schema]{3}, so state is always native-reported or absent, never inferred. No confidence field exists in the Status record documented there. This satisfies the "inferred state must be visibly distinguished" guardrail by construction, at the price of invisible sessions.

## Q3. Clients

- Desktop app on the MacBook to a remote Mac mini core: supported. Add an SSH machine; spaces on it "run their terminals there"; "Connected screens share that structure and the live terminals, but keep their own focus and zoom" [hma-core-app-readme]{6}. Core-to-core uses `hc machine add` over SSH or `--via` [hma-core-docs-machines]{2} [hma-core-docs-machines]{3}; Tailscale is not named in the machines doc [hma-core-docs-machines]{7}, but the mobile page says Tailscale SSH works without a key [hma-herdr-site-product-pages]{7}.
- Plain terminal: `hc ls`, `hc attach <name>` (Ctrl+\ detaches), `hc read` [hma-core-readme]{3}. There is no official core TUI: users report "one terminal at a time, no list of agents and their states, no tabs or splits" over SSH [hma-core-issue-25-tui-client]{3}; whether one is planned is unanswered in the thread [hma-core-issue-25-tui-client]{5}. An unofficial `hc-tui` v0.1.0 exists with macOS arm64 binaries, unverified on a Mac by its author [hma-core-issue-25-tui-client]{4}.
- Concurrent clients: yes by design (multiple viewers; the last active viewer sets the terminal size) [hma-core-app-readme]{6} [hma-core-api-schema]{8}; the changelog notes a terminal "another device (your phone) resized" takes its size back on focus [hma-core-app-readme]{8}. Concurrency defect #5749 (second client stalls on a Claude Code tab) is filed against the TUI, not core [hma-herdr-open-issues]{5}.
- The app's own control socket is local, so nothing on the host can drive the window [hma-core-issue-25-tui-client]{3}.

## Q4. Official Herdr mobile app on Android

- Play listing: package dev.herdr.app, developer Herdr, Inc., price 0, version 1.0.5, updated Nov 9, 2026, downloads bucket "0+", no rating displayed, data safety "No data collected" [hma-core-play-herdr-listing]{1} [hma-core-play-herdr-listing]{2} [hma-core-play-herdr-listing]{10}. Free per the site too [hma-core-site-mobile-privacy-faq]{10}. iPhone and iPad builds also exist [hma-herdr-site-product-pages]{11}.
- Inbox ordering: "needs you, done, working, idle"; blue dot for unread; swipe left sends Esc, right pins or marks read [hma-herdr-site-product-pages]{6} [hma-core-play-herdr-listing]{4}. Per-agent pinning and read state are shared with the desktop through core labels [hma-core-app-docs-labels]{1}.
- Notifications: the only documented alert is "While the app is open, a banner tells you when an agent needs you or is done" [hma-core-site-mobile-privacy-faq]{1}. Neither the Play description nor the mobile page mentions push when the app is closed [hma-core-play-herdr-listing]{9}. The privacy page says the app talks only to your machines over SSH with no server of the vendor's in between [hma-core-site-mobile-privacy-faq]{9}, which is consistent with no vendor push relay, but that inference is not stated in the sources. {inferred: closed-app push is absent or undocumented}
- Approvals: keystrokes, not structured actions. The phone shows the real terminal with a key bar (Esc, Tab, Ctrl, arrows) and a compose box that sends "one paste, then Enter" [hma-core-play-herdr-listing]{5} [hma-core-site-mobile-privacy-faq]{5}. No approve/deny button is described. Core refuses a normal `send` to a `blocked` terminal unless forced [hma-core-docs-commands-skill]{2}, but that is a CLI/API guard and "not an access boundary against another client" [hma-core-docs-security]{3}.
- Labels visible: spaces and tabs from the desktop app appear, and you can "rename a tab from the phone" [hma-core-play-herdr-listing]{6}. Spaces "show up when the Herdr app runs there too"; with core alone, "Terminals and agents show up either way" [hma-core-site-mobile-privacy-faq]{2}. For a headless Mac mini this means per-session space/tab labels may require the desktop app to be running on the mini; that requirement is stated, whether it can run without a logged-in GUI session is not documented.
- Setup: the app generates its own SSH key; add its public key once or use Tailscale SSH [hma-core-play-herdr-listing]{7}. Day-one reports say the Android app asks for a password without trying key auth [hma-core-app-issues-mobile]{1} and that connecting the desktop to the phone app is unclear [hma-core-app-issues-mobile]{2}; both are single-reporter, untriaged.

## Q5. Labels and names

- Core terminal name: `hc run --name`, "1-32 of a-z 0-9 - _", unique among live terminals [hma-core-docs-commands-skill]{9}. A `project: feature` string with colon and space does not fit; `project-feature` does.
- Free-form `key=value` labels via `hc label`, "never interpreted" by core [hma-core-api-schema]{6}; clients use the `herdr.` prefix for seen and pinned [hma-core-app-docs-labels]{5}. Whether the app or phone render arbitrary labels as titles is not documented.
- Space and tab names: "Name a space or tab when you want a label that stays" [hma-core-app-readme]{3}; spaces and tabs are stored in each machine's core [hma-core-app-readme]{6}. After a reboot, users report "layout and tab names kept, as documented" [hma-core-issues-resume-recovery]{7} and "space/tab labels were intact" [hma-core-issues-resume-recovery]{8}; one Linux report said spaces were not visibly restored on a core 0.1.14 / app 0.1.9 build, left open [hma-core-issues-resume-recovery]{7}. The phone lists spaces and renames tabs [hma-core-play-herdr-listing]{6}. So `project: feature` can live in tab names, visible on all three clients, if the desktop app is running on the host; unproven on this host.

## Q6. Persistence and recovery

- Client loss: terminals live in the core; "Closing your viewer does not end the program" [hma-core-readme]{3}; remote work "keeps running when your local window closes or your laptop sleeps" [hma-core-app-readme]{6}. Unlike the TUI's open #5170 (Linux client drop kills panes) and #5471/#5624 remote stalls [hma-herdr-open-issues]{1} [hma-herdr-open-issues]{2} [hma-herdr-open-issues]{4}, no equivalent core client-drop defect was seen in the issues read. {inferred: absence in a sample, not a negative proof}
- Core restart or update: holders keep programs running; `hc update` and `hc server restart` leave terminals running [hma-core-readme]{2} [hma-core-docs-commands-skill]{7}. "Killing only the core process lost nothing" (Linux report) [hma-core-issues-resume-recovery]{6}.
- Host reboot: "If the machine reboots or herdr-core stops, the programs stop too. Their panes come back with a shell in the same folder, but Herdr doesn't restart an agent or resume its work in progress" [hma-core-site-mobile-privacy-faq]{6}; recovery needs `--keep` and "never reruns the task" [hma-core-readme]{4}. Native resume for Claude/Codex: none. A maintainer said it "waits until the protocol has a way for agents to report how to resume" [hma-core-issues-resume-recovery]{2}; the proposal #15 is open [hma-core-issues-resume-recovery]{4}. Users on macOS with Claude Code confirm all sessions lost [hma-core-issues-resume-recovery]{7}. The TUI, by contrast, claims "restart the machine and Herdr brings the layout back and resumes their sessions" [hma-herdr-site-product-pages]{12}, though open resume-identity bugs exist for Codex and Claude (#5837, #5909) [hma-herdr-open-issues]{9}.

## Q7. Ecosystem compatibility

- Moshi: its Herdr page calls `herdr session list --json` and reads `$HERDR_ENV`/`$HERDR_SESSION` [hma-android-moshi-docs-herdr]{2} [hma-android-moshi-docs-herdr]{7}, and a re-grep of that page found no mention of herdr-core, `hc` or 7501 [hma-core-moshi-herdr-page-recheck]{1}. Moshi's Herdr integration therefore targets Herdr TUI conventions; core support is not documented. Moshi's push and approvals come from moshi-hook [hma-android-moshi-play-listing]{4}, whose Herdr tagging is the only Herdr-specific part [hma-android-moshi-docs-herdr]{2}; whether the hook push works for agents in core panes is not documented. {extends: plausible because hooks run in the agent process, untested} A Moshi SSH terminal could still run `hc attach` manually [hma-core-readme]{3} {inferred}.
- wherdr: uses the Herdr API socket `~/.config/herdr/herdr.sock` and `herdr terminal session control` [hma-wherdr-docs]{4}; core's socket is `<session>.sock` under the runtime or state directory [hma-core-docs-security]{5}. Core is not mentioned in the docs read, so wherdr with core is not documented. {inferred: wherdr does not see core terminals}
- Shepherdr (ex herdr-projects 3.x): "mission control for herdr-core, as a layout for the Herdr app", needs Herdr app 0.1.12+ and herdr-core 0.1.17+ plus Python, Git and Claude Code or Codex; adds a Coordinator, per-task worktrees, a second-agent review and a Needs-you board [hma-herdr-projects-readme]{4}. The 1.x line targets the TUI and wherdr's Board refuses Shepherdr 2.x [hma-herdr-projects-readme]{5}.
- TUI and core do not share agents: "what runs in one doesn't show up in the other"; both can run on one machine [hma-core-site-mobile-privacy-faq]{8} [hma-core-site-mobile-privacy-faq]{3}.

## Q8. Third-party status into herdr-core

- API: the OpenRPC method list has no call that sets a terminal's status [hma-core-api-schema]{5}; status enters only as OSC 7501 in the terminal's output [hma-core-api-schema]{3}. `terminal.label` and `doc.set` accept free data but are not status [hma-core-api-schema]{6} [hma-core-api-schema]{4}.
- Hook path works: a third party verified that writing `ESC ] 7501 ; : state=idle : app=claude-code ESC \` to the Claude process's tty flipped a pane to `reported: true`, using a hook that walks up to an ancestor with a tty because a hook has no controlling tty [hma-core-app-issue-537]{5} [hma-core-app-issue-537]{6}. The documented one-liner for scripts is `printf '\e]7501;state=blocked:app=my-agent\e\\'` [hma-herdr-site-product-pages]{3}.
- So an external observer (Claude hooks, a Codex app-server watcher) can supply native state only by writing OSC 7501 to the pane's tty on the same machine. {inferred: a Codex app-server observer would need a tty-write path; none documented} Status records support child ids and `clear` [hma-core-api-schema]{8}.

## Disconfirming analysis

- "Core is better because status is native": searched for core failures to report. Claude Code's one-shot probe can leave a session unreported for its lifetime [hma-core-app-issue-537]{3}; backgrounding stops it [hma-core-claude-code-osc7501-issues]{5}; Codex can hold `working` for hours [hma-core-codex-osc7501-issues]{3}. The claim holds in direction (no screen scraping, so no wrong guess) but not as reliability: the failure mode is invisible sessions. For a supervision tool that routes attention, a missing session is a worse failure than a mislabelled one. {inferred}
- "Core avoids the TUI's remote defects": the TUI defects cited are in herdrdev/herdr; core's issues were only sampled (106 open) and its macOS hosting defects (#104, #203, #12) are directly on the headless-SSH path [hma-core-issues-macos-hosting]{1}. No evidence of better remote reliability, only absence in sample.
- "Official Android app solves notifications": searched Play listing, mobile page and issue titles for closed-app push; found none [hma-core-play-herdr-listing]{9} [hma-core-app-issues-mobile]{3}. Not shown to exist; not shown absent beyond text read.
- "Core resumes like the TUI": searched; maintainers state it does not [hma-core-issues-resume-recovery]{2}.
- "Labels are free": searched; terminal names are 1-32 chars of a restricted set [hma-core-docs-commands-skill]{9}; free-form labels are not documented as shown on phone.

## Contradictions

- Claude Code native OSC 7501: the issue #537 original reporter states "Claude Code doesn't send OSC 7501 itself" [hma-core-app-issue-537]{1}; a commenter on the same issue measures `programStatus=yes` and status under hc [hma-core-app-issue-537]{2}; Claude Code issue reports describe native emission since 2.1.295 [hma-core-claude-code-osc7501-issues]{1}. Positions stand side by side; relation: `contradicts` on whether it emits, resolvable by the probe's startup dependence ({ambiguous: the probe-timing explanation is in [hma-core-app-issue-537]{3})}).
- Status method: herdr.dev says core "draws nothing and guesses nothing" with no screen scraping [hma-herdr-site-product-pages]{9}; the TUI page says Herdr "reads every pane and marks each agent" [hma-herdr-site-product-pages]{12}. {incommensurable: two different products with different detection models.}
- Reboot: the TUI is described as resuming sessions [hma-herdr-site-product-pages]{12}; the app/core FAQ says no resume [hma-core-site-mobile-privacy-faq]{6}. `tension` across products, not a contradiction. Issue #13 is closed while #15 (the actual work) is open [hma-core-issues-resume-recovery]{1} [hma-core-issues-resume-recovery]{4}; closure does not mean delivery.
