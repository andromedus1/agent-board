# Herdr ecosystem facet

Scope: the operator's proposed stack runs Herdr TUI on an always-on Mac mini and reaches it by SSH over Tailscale from a MacBook Air and an Android phone (Moshi), with wherdr and Herdr Projects optional later. Fetch date 2026-11-10; Herdr TUI stable at the time is v0.9.5.

## Headline findings

1. The "Herdr" name now covers three products, and the phone story differs by product. The official mobile app (iPhone, iPad, Android) "isn't supported" with Herdr TUI and talks only to herdr-core [hma-herdr-site-product-pages]{4}[hma-herdr-site-product-pages]{5}. For Herdr TUI the official phone path is any SSH client; the docs name Moshi for iPhone and name no Android client [hma-herdr-tui-remote-docs]{8}.
2. For Claude Code and Codex, Herdr TUI state is still inferred from the screen; the installed hooks report only session identity [hma-herdr-tui-agents-notify-docs]{1}[hma-herdr-tui-agents-notify-docs]{3}. v0.9.5 removed the Codex turn hooks again [hma-herdr-releases]{2}.
3. Blocked detection is "deliberately strict" and an unmatched prompt falls back to idle; the docs themselves say idle "is not authorization to approve an action" [hma-herdr-tui-agents-notify-docs]{4}. This bears directly on the operator's low-noise and no-false-reassurance priorities.
4. Persistence is process-level only while the server lives. A server stop or host reboot kills panes; layout comes back and Claude/Codex are relaunched with native resume where an official integration recorded a session id [hma-herdr-tui-session-state-docs]{1}[hma-herdr-tui-session-state-docs]{3}[hma-herdr-tui-session-state-docs]{5}.
5. Open defects relevant to this topology: macOS remote stream stall #5624, second-client stall on a shared Claude tab #5749, SSH probe lockout #5634, and the Linux-labelled #5170 and #5471 [hma-herdr-open-issues]{1}[hma-herdr-open-issues]{2}[hma-herdr-open-issues]{4}[hma-herdr-open-issues]{5}[hma-herdr-open-issues]{6}.
6. wherdr exists, is third-party and unofficial, and does work against a Herdr TUI server because it uses the server's local socket [hma-wherdr-docs]{1}[hma-wherdr-docs]{4}. Herdr Projects exists, is third-party, and its 1.x line is the TUI-compatible one; the project has since pivoted to the Herdr app / herdr-core as Shepherdr [hma-herdr-projects-readme]{3}[hma-herdr-projects-readme]{4}.

## Q1. Herdr TUI vs Herdr Desktop

- **Three pieces.** The Herdr app (desktop), herdr-core (`hc`, a runtime installable alone), and Herdr TUI; the app and core are built together, and "The app, herdr-core and Herdr TUI are open source under Apache 2.0" [hma-herdr-site-product-pages]{2}. Herdr TUI is "v0.9.5" per its own page [hma-herdr-site-product-pages]{12}; v0.9.5 was published 2026-10-14 as a hotfix on v0.9.4 (2026-10-13) [hma-herdr-releases]{1}[hma-herdr-releases]{2}. No stable tag later than v0.9.5 existed at fetch [hma-herdr-releases]{1}. The app/core repositories carry separate versions (the Shepherdr README cites herdr-app 0.1.12+ and herdr-core 0.1.17+) [hma-herdr-projects-readme]{4}.
- **Architecture.** TUI: "a background server plus one or more attached clients"; the server owns panes and process state [hma-herdr-tui-remote-docs]{12}. herdr-core: terminals live in a server rather than the window, and the same API is open to third-party clients [hma-herdr-site-product-pages]{2}[hma-herdr-site-product-pages]{10}.
- **Which fits the topology.** Both are headless-capable in principle. TUI supports headless server use (`herdr server` "for supervised or service-style setups"; a 120x40 virtual size when no client is attached) [hma-herdr-tui-remote-docs]{13}[hma-herdr-tui-remote-docs]{14}. herdr-core can be installed "on its own" for servers [hma-herdr-site-product-pages]{11}. The decisive difference for the operator is the phone: the official app connects to herdr-core only [hma-herdr-site-product-pages]{5}, so choosing TUI forgoes the official mobile app; this also means a TUI-vs-core choice is a phone-client choice. {inferred: convergence of mobile FAQ and the operator's TUI plan}
- **macOS as server host.** Supported: remote attach targets "Linux or macOS" servers on x86_64 or aarch64 [hma-herdr-tui-remote-docs]{6}. The server ignores SIGHUP on Linux and macOS [hma-herdr-tui-remote-docs]{9}, and the v0.9.4 notes say closing the starting shell "no longer stops the server" on both [hma-herdr-releases]{4}. A master-branch fix keeps "the macos server running when its terminal quits (#5236)" and is not in v0.9.5 absent a later tag [hma-herdr-releases]{6}. The fetched docs describe no launchd unit, login item, or boot-time start for Herdr TUI, and no behaviour before first GUI login; they only mention "automatically started macOS servers" using "a per-user service context" [hma-herdr-tui-troubleshooting-docs]{2}[hma-herdr-tui-troubleshooting-docs]{5}. Launch-at-boot for the TUI server is therefore not documented. wherdr's installer sets automatic startup "at login on macOS" for itself [hma-wherdr-docs]{2}, which is a different thing from starting Herdr.
- **macOS-specific caveats (documented).** A server started through SSH or a background job "may not have access to interactive Keychain services"; the docs advise starting Herdr from a normal GUI terminal [hma-herdr-tui-troubleshooting-docs]{1}. After logout an older server can lose user lookup and DNS; recovery requires a restart from a GUI terminal, which "ends live pane processes" [hma-herdr-tui-troubleshooting-docs]{3}. These bear on a no-login Mac mini; whether FileVault/pre-login is the better frame belongs to the mac-mini-headless-host facet.
- **macOS defects tied to the desktop/core line, not the TUI.** #5905 (panes outside the user launchd session, DNS fails) and #5784 are reported against the desktop app / `herdr-core`; a commenter's control test found "the Herdr CLI does not have this problem" [hma-herdr-open-issues]{7}[hma-herdr-open-issues]{8}.

## Q2. Remote attach, concurrency, survival

- **Paths.** (a) `ssh host` then `herdr` ("works like a terminal multiplexer", the recommended path for phone SSH clients); (b) `herdr --remote host` with a local UI over an SSH bridge; (c) saved machines (`herdr machine add`) for several servers in one client [hma-herdr-tui-remote-docs]{8}[hma-herdr-tui-remote-docs]{10}[hma-herdr-tui-remote-docs]{1}. Remote auth is OpenSSH, with ssh-agent loading required for passphrase keys in a "mobile terminal" [hma-herdr-tui-remote-docs]{10}.
- **Concurrent clients.** Multiple clients may attach; each can view its own workspace/tab, and for a shared tab "the last one to focus, select, or interact with it controls that tab's pane sizes" [hma-herdr-tui-remote-docs]{12}. A direct terminal attach has a single writable owner, with `--takeover` [hma-herdr-tui-remote-docs]{11}. Defect: with macOS 26.5 and Claude Code in the shared pane, the second client "becomes unusable for a minute or more" (#5749, open p1) [hma-herdr-open-issues]{5}. A laptop-plus-phone session on the same tab is the case the operator proposes, so this is a direct risk; views of different tabs are not reported broken. {inferred: mapping of #5749 onto the laptop+phone topology}
- **Detach and client loss.** `ctrl+b q` detaches and panes keep running; the dropped-client case on a saved machine "leaves the remote Herdr server, sessions, and pane processes running" [hma-herdr-tui-remote-docs]{9}[hma-herdr-tui-remote-docs]{4}. Contrary report: #5170 says dropping the SSH client kills the remote server on a Linux host (see Contradictions) [hma-herdr-open-issues]{1}.
- **Sleeping client.** Saved-machine connections close their bridge after a minute without traffic, with sleep counted toward it [hma-herdr-tui-remote-docs]{4}. Separately, #5471 reports unbounded server memory growth while a client is attached but not reading, including a laptop that sleeps (about 4 MB per minute in the reproduction; 8.3 GB after 27 days in a second reporter's stable-0.9.3 case with about 25 panes) [hma-herdr-open-issues]{2}. Both reports are Linux-labelled and still open; the macOS exposure is unknown. {inferred: platform extrapolation not tested}
- **Survival matrix.** Detach/reattach: processes, layout and conversation survive. Server restart: processes do not; layout does; conversation only with native agent resume [hma-herdr-tui-session-state-docs]{1}. Host reboot is a server restart. On a Mac restart, v0.9.4 "saves before the system starts closing apps" [hma-herdr-releases]{3}; a Linux-only logind shutdown delay is the documented analogue elsewhere, and power loss is not covered [hma-herdr-tui-session-state-docs]{4}. Whether a macOS power cut is covered is not documented; snapshots are retained (up to 48) [hma-herdr-tui-session-state-docs]{4}.
- **Native resume for Claude/Codex.** Enabled by default; Claude Code needs integration version 6 (`claude --resume <id>`) and Codex version 5 (`codex resume <id>`); stale or missing references restore as plain shells [hma-herdr-tui-session-state-docs]{5}. Open bugs affect correctness: #5837 (Codex pane's recorded session replaced by its auto-review subagent thread), #5909 (Claude `/branch` restores the pre-branch conversation) [hma-herdr-open-issues]{9}.
- **After reboot, who restarts the server?** Not documented for the TUI. Running `herdr` auto-starts a server per the troubleshooting page's "automatically started" wording [hma-herdr-tui-troubleshooting-docs]{1}, and resume of eligible panes begins "After a client attaches" [hma-herdr-tui-session-state-docs]{5}. Restored agents on a headless Mac therefore appear to need a client attach or an external launcher. {inferred: composed from the two passages}

## Q3. Labels and context

- The CLI offers `workspace create --label`, `workspace rename`, `tab rename`, `pane rename`, and `agent rename` for display [hma-herdr-tui-agents-notify-docs]{7}. A `project: feature` label could be carried as workspace label (project) plus tab or pane/agent label (feature). {inferred: mapping}
- Persistence of those labels across a server restart is not documented in the pages read; session restore is described as "workspaces, tabs, panes, cwd, layout, and focus" [hma-herdr-tui-session-state-docs]{3}. Metadata tokens (`summary`, per-state text) are "display-only" and "not restored after a server restart" [hma-herdr-tui-agents-notify-docs]{8}.
- Visibility in remote clients: in `herdr --remote` and saved-machine modes the client draws the sidebar from server state, with a machine token on agent rows when several machines exist [hma-herdr-tui-remote-docs]{10}[hma-herdr-tui-remote-docs]{2}; the cached view is dimmed on disconnect [hma-herdr-tui-remote-docs]{3}. In a phone SSH client the TUI itself is the display. Auto-titling plugins exist (herdr-auto-title: branch, process, agent session names) but were read at description level only [hma-herdr-ecosystem-search]{1}.

## Q4. Status detection

- Claude Code and Codex are "Supported by Herdr" meaning Herdr "reads their state from what they draw on screen"; the integration hook reports session identity only [hma-herdr-tui-agents-notify-docs]{1}[hma-herdr-tui-agents-notify-docs]{3}. Agents that "support Herdr" (e.g. Kimi, OpenCode, Pi) can report lifecycle state [hma-herdr-tui-agents-notify-docs]{1}[hma-herdr-tui-agents-notify-docs]{2}. Both agents are in the 22-entry screen-manifest list on master [hma-herdr-source-master]{2}.
- **Change since 2026-10-26:** none found for Claude/Codex authority. The relevant change predates it: v0.9.4 had Codex reporting finished turns through its integration; v0.9.5 (2026-10-14) removed Codex turn hooks and "Codex status comes from screen detection again" [hma-herdr-releases]{5}[hma-herdr-releases]{2}. Manifests are also remotely updated from herdr.dev unless disabled [hma-herdr-tui-agents-notify-docs]{9}, so detection rules can change without a binary update.
- **States:** idle, working, blocked, done (idle and not yet seen), unknown [hma-herdr-tui-agents-notify-docs]{6}. There is no "failed/error" state; the operator's failed state has no native equivalent in these docs. {inferred: absence in documented value set}
- **Rollups and ordering:** blocked makes pane/tab/workspace blocked; a done agent stays visible until viewed [hma-herdr-tui-agents-notify-docs]{5}; priority is blocked, then unseen idle, then working, then seen idle, then unknown [hma-herdr-source-master]{1}. Done-badge seen state is tracked per client [hma-herdr-tui-agents-notify-docs]{6}, which matters for laptop plus phone.
- **Inferred vs native distinction:** `herdr agent explain` shows the matched rule, manifest source and "default_known_agent_idle_fallback" [hma-herdr-tui-agents-notify-docs]{9}[hma-herdr-tui-agents-notify-docs]{4}; the docs do not describe an on-screen indicator in the sidebar that separates screen-inferred from hook-reported state. Not documented.

## Q5. Notifications, hooks, approvals

- **Built-in:** toast (in-app), terminal (outer-terminal notification that "also works over SSH"), system (macOS via terminal-notifier, else a Script Editor-attributed osascript fallback), or off; suppressed for the active tab; sound plays through the local client [hma-herdr-tui-agents-notify-docs]{10}. For a phone SSH client, the `terminal` route depends on the client's OSC handling, which is the android-access facet's concern.
- **Events/streams:** `events.subscribe` (including `pane.agent_status_changed`), non-durable with `events_lost` on lag; `notification.show`; read-only terminal observers and one writable controller [hma-herdr-tui-agents-notify-docs]{11}; [hma-herdr-tui-remote-docs]{11}. Plugins can hook events [hma-herdr-tui-agents-notify-docs]{11}.
- **Approvals:** no structured approve/deny method appears in the pages read; the control surface is key and text injection (`agent send-keys`, `pane.send_keys`, `pane.send_text`, `agent prompt`) [hma-herdr-tui-agents-notify-docs]{12}. Approval through Herdr is therefore keystrokes into the pane, with the agent's own prompt as the semantic layer. This matches the guardrail that a keystroke is not semantic approval only if the UI makes the operator read the prompt. Herdr's docs add a warning that "automation that trusts a mistaken idle state can type into an approval dialog" [hma-herdr-tui-agents-notify-docs]{4}.

## Q7. Security of remote mode

- Remote attach and saved machines rely on OpenSSH for authentication and transport; Herdr stores no passwords, keys, or control sockets [hma-herdr-tui-remote-docs]{5}[hma-herdr-tui-remote-docs]{10}. The server API is a Unix domain socket under `~/.config/herdr/` [hma-herdr-tui-agents-notify-docs]{13}; the pages read document no TCP listener and do not state socket permissions. Remote CLI/API calls travel over non-interactive SSH [hma-herdr-tui-remote-docs]{7}. So the operator's Tailscale-plus-SSH setup adds no Herdr-specific network exposure on the evidence read. {inferred: from absence of any documented listener}
- Hardening note from defects: saved-machine probe bursts can trip sshd penalties (#5634) [hma-herdr-open-issues]{6}.

## Q8. wherdr

- **What:** "an unofficial, self-hosted web client for Herdr", third-party (afloury), MIT, created 2026-09-27, v2.5.0 on 2026-11-02, releases about every two days in late October [hma-wherdr-docs]{1}. Maturity: five weeks old, 16 stars, rapid churn and a 1.x to 2.0 breaking change [hma-wherdr-docs]{1}. Not the same as the older `derekr/wherdr` [hma-herdr-ecosystem-search]{2}.
- **Fit:** runs on the Herdr host, uses `~/.config/herdr/herdr.sock`, `herdr terminal session control` for the terminal view, and read-only transcript files [hma-wherdr-docs]{4}; requires Herdr >= 0.9.1 on macOS or Linux [hma-wherdr-docs]{2}. It reads `~/.claude` and `~/.codex` transcripts in addition to Herdr's state, i.e. it adds a transcript-derived view beyond Herdr's screen inference. {inferred: from the architecture diagram}
- **Install/auth/network:** one-line installer; macOS startup at login; localhost:7683; Tailscale Serve for HTTPS; optional passkey lock; "Without a passkey, anyone who can reach the address can control your agents" [hma-wherdr-docs]{2}[hma-wherdr-docs]{5}. It is "a remote shell as your user" [hma-wherdr-docs]{3}. Funnel exposure causes refusal [hma-wherdr-docs]{5}.
- **Notifications/PWA/Android:** installable PWA; Android via Chrome "Install app"; Web Push on blocked (with question and options) or done, with per-device delivery results and Do-not-disturb [hma-wherdr-docs]{7}[hma-wherdr-docs]{6}. Android usability beyond install steps was not tested. Push on Android behaviour with a sleeping device is a facet-3/android concern.
- **Approvals:** native questions and approvals have one-tap controls; unrecognised screens fall back to the real terminal with y/n and arrow keys [hma-wherdr-docs]{8}. Whether the one-tap path sends text or keys to the pane is not stated at API level. Because wherdr drives Herdr's socket, approvals still end as input into the pane. {inferred: architecture}
- **Login-time start on macOS** is relevant to the no-GUI-login question and is the installer's, not Herdr's [hma-wherdr-docs]{2}.

## Disconfirming analysis

- *Claim: Claude/Codex status is inferred, not native.* Searched for any change: the docs re-fetch, the v0.9.4 to v0.9.5 notes, and master's agent list. The only counter-signal was v0.9.4's Codex turn-hook reporting, reverted in v0.9.5 [hma-herdr-releases]{5}[hma-herdr-releases]{2}; the integration pages still say state comes from screen detection [hma-herdr-tui-agents-notify-docs]{3}. The claim stands for stable v0.9.5; a future release could change it.
- *Claim: the official mobile app does not serve a TUI deployment.* Looked for any caveat: the mobile page, FAQ and download page all say TUI is unsupported [hma-herdr-site-product-pages]{4}[hma-herdr-site-product-pages]{5}[hma-herdr-site-product-pages]{11}. No source disagrees.
- *Claim: client loss does not kill panes.* Disconfirming evidence exists: #5170 [hma-herdr-open-issues]{1}. It is Linux-labelled, is a single report with a maintainer non-repro, and contradicts the documented design; kept as an open risk rather than resolved (see Contradictions).
- *Claim: macOS is a supported server host.* Searched for macOS-specific breakage: #4391 (cosmetic), #5624 and #5749 (functional, open) are the macOS items on the TUI line [hma-herdr-open-issues]{3}[hma-herdr-open-issues]{4}[hma-herdr-open-issues]{5}; #5905/#5784 are desktop-app items [hma-herdr-open-issues]{7}[hma-herdr-open-issues]{8}. Support is documented; reliability at 5 to 15 sessions with two clients is not established by any source read.
- *Claim: no structured approval path.* Searched the socket API listing and CLI reference for an approve/deny method; none found among the methods named [hma-herdr-tui-agents-notify-docs]{12}. Absence is in the pages read, not a proof for the whole API schema.
- *Claim: wherdr works with TUI.* Disconfirming check: its docs depend on Herdr's local socket, not herdr-core specifically [hma-wherdr-docs]{4}; the README does not name TUI explicitly. Not run here.

## Contradictions

- **Client loss and pane survival.** Herdr docs: the server ignores SIGHUP so a hangup from its launching shell does not stop panes, and bridge cleanup "leaves the remote Herdr server, sessions, and pane processes running" [hma-herdr-tui-remote-docs]{9}[hma-herdr-tui-remote-docs]{4}. #5170 reporter: `herdr --remote` starts a server that "dies when the local client or SSH session drops. Every pane process is killed" [hma-herdr-open-issues]{1}. Maintainer: could not reproduce over Tailscale SSH with `KillUserProcesses=false` [hma-herdr-open-issues]{1}. Positions stand side by side. {ambiguous: #5170 reproduction conditions}
- **Phone support framing.** Herdr TUI docs: "Herdr works on your phone without a mobile app or web dashboard" via an SSH client [hma-herdr-tui-remote-docs]{8}. Herdr mobile page: the phone app does not support TUI [hma-herdr-site-product-pages]{5}. These are compatible only if "phone support" means different things; the first is a terminal in an SSH client, the second a native inbox app. {incommensurable: terminal-in-SSH vs native Inbox app}
- **Status authority framing.** Core page: status is "no screen scraping" via OSC 7501 [hma-herdr-site-product-pages]{9}; TUI docs: Claude/Codex are read from the screen [hma-herdr-tui-agents-notify-docs]{1}. Different products, not a conflict, but easily conflated. {contested: which model the operator's Claude/Codex sessions get depends on product line}
