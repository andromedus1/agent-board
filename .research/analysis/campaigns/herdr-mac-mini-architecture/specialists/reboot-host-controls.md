# Reboot host controls

Seed: always-on Apple-silicon Mac mini (2024 or later, macOS 26), FileVault on, no automatic login, Herdr TUI under a standard "agent" user, reached by Remote Login and open-source `tailscaled` as a LaunchDaemon. Citation form `[handle]{N}` resolves to the numbered key passage in the named attestation. Unmarked statements are carried by the cited attestation; `{inferred}` and `extends` mark composition. Sources describing the operator laptop (not the Mac mini) are named as such.

## 1. Update control

**Recommended settings (unmanaged Mac).**

- System Settings > General > Software Update > Automatic Updates has three toggles: "Download new updates when available", "Install macOS updates", and "Install Security Responses and system files" [hma-reboot-apple-macos-autoupdates]{1}. Turn off "Install macOS updates" so OS updates do not install and restart overnight; the page states that updates can install overnight while the Mac is connected to power and asleep [hma-host-apple-platform-support-updates]{1}. Leaving "Download new updates" on is compatible with this, because downloaded updates install later through `softwareupdate --install` or System Settings [hma-reboot-man-softwareupdate]{6}. `extends`: keeping download on and install off is a composed combination; no fetched page recommends it.
- System Settings > Privacy & Security > Background Security Improvements > turn off "Automatically Install" [hma-reboot-apple-bsi-support]{3}. With it off, the Mac "will not receive these improvements until they're included in a subsequent software update" [hma-reboot-apple-bsi-support]{4}.
- Run updates by hand in a chosen window: `softwareupdate --list` (exempt from the admin-authentication requirement), `--download`, then `sudo softwareupdate --install --os-only --restart` [hma-reboot-man-softwareupdate]{2}. With `--restart`, a logged-in invoking user gets a quit-all-apps, logout and restart attempt, while a not-logged-in invoker gets "a forced reboot if necessary" [hma-reboot-man-softwareupdate]{3}. Run the update after a deliberate `herdr server stop` or detach, not under live agents. `extends`: the sequencing is composed.
- There is no `softwareupdate` verb that disables automatic download or installation; `--schedule` only "Returns the per-machine automatic (background) check preference" [hma-reboot-man-softwareupdate]{7}[hma-reboot-man-softwareupdate]{8}. The operator laptop printed "Automatic checking for updates is turned on" and showed preference keys `AutomaticallyInstallMacOSUpdates` and `CriticalUpdateInstall` [hma-reboot-local-softwareupdate-state]{1}[hma-reboot-local-softwareupdate-state]{2}; scripting those keys with `defaults write` is practitioner folklore, not attested, so use the Settings toggles.

**Background Security Improvements (BSI), macOS 26.1 and later.**

- Supported and enabled starting macOS 26.1 [hma-reboot-apple-bsi-support]{1}, applied automatically by default, with "a prompt ... asking to restart the device" where a restart is needed [hma-reboot-apple-bsi-platform-support]{3}.
- Restart behaviour: BSIs that involve the operating system "require the device to restart"; on Mac the content can reach Safari with only a process relaunch, "though a restart is required to make this content broadly available to the rest of the operating system" [hma-reboot-apple-bsi-platform-support]{1}. A BSI can therefore force a restart prompt on a Mac that is left at default settings. `{inferred: the page says a prompt appears; it does not say whether the prompt auto-confirms on an unattended Mac.}`
- Deferral: BSIs "don't adhere to the managed software update delay", but are effectively delayed if the minor OS update they belong to is delayed [hma-reboot-apple-bsi-platform-support]{2}. A user can remove an applied BSI, which removes all applied since the last software update [hma-reboot-apple-bsi-platform-support]{7}.
- The cost of switching BSI off: fixes then wait for the next software update [hma-reboot-apple-bsi-support]{4}. Treat this as a security trade the operator accepts and schedules around, not a free control.

**Rapid Security Responses (RSR).** The Mac User Guide page served on 2026-11-10 still names "Install Security Responses and system files" and mentions Rapid Security Responses [hma-reboot-apple-macos-autoupdates]{1}, while Apple's BSI pages describe BSI as the mechanism for 26.1 and later [hma-reboot-apple-bsi-support]{1}. `{ambiguous: no fetched page states whether the "Security Responses and system files" toggle governs BSI, RSR, or only XProtect-style data updates; the deployment page describes the Mac security-updates setting as covering "XProtect, Gatekeeper, and system data files" [hma-reboot-apple-deploy-enforce-updates]{7}.}` Practical reading: leave that toggle on if the operator accepts the risk of unknown restarts being absent from XProtect-style updates, `{inferred}` because the deployment page does not say those updates restart the Mac.

**What needs MDM.** Time-based deferral of 1 to 90 days is described for supervised devices [hma-reboot-apple-deploy-enforce-updates]{1}, as is control of automatic update behaviour on "supervised devices" [hma-reboot-apple-deploy-enforce-updates]{2}. Organisations can enforce an update at a chosen time "regardless of configured deferrals or if the automatic installation of Background Security Improvements is turned off", force-quitting all apps and restarting if necessary, using a bootstrap token on Apple silicon if available [hma-reboot-apple-deploy-enforce-updates]{4}[hma-reboot-apple-deploy-enforce-updates]{5}. `{inferred: because these pages are written for device-management services, an unmanaged Mac has the Settings toggles and the CLI only; no deferral timer exists without MDM. The reading rests on page scope, not on an explicit Apple statement.}` Enforcement is an MDM-side action and cannot occur on an unmanaged Mac.

## 2. authrestart on Apple silicon

- `fdesetup authrestart` is documented "on supported hardware", and "The command may not work on all systems" [hma-host-man-fdesetup]{1}[hma-host-man-fdesetup]{4}. `fdesetup supportsauthrestart` "Returns the string 'true' if the system supports the authenticated restart option", but FileVault must also be on [hma-reboot-man-fdesetup-authrestart]{3}[hma-reboot-man-fdesetup-authrestart]{5}. On the operator laptop (Apple silicon, Mac17,3, macOS 26.6, FileVault on) it printed `true` [hma-reboot-local-softwareupdate-state]{3}. That is one data point from a different model than the Mac mini; run `fdesetup supportsauthrestart` on the mini, a read-only command with no sudo, before relying on it.
- No fetched Apple text says authrestart is supported or unsupported on macOS 26 Apple silicon specifically. An Apple Developer Forums thread asking about its security implications drew a DTS reply declining to answer, per a tool-processed extract [hma-reboot-apple-dev-forum-authrestart]{1}[hma-reboot-apple-dev-forum-authrestart]{2}, and `{confidence: search-summary}` applies. A practitioner article says Apple uses authenticated restarts in updates, that on Apple silicon they are handled by the Secure Enclave, and that the authorising token "can only be used once" [hma-reboot-eclectic-authrestart]{1}; this is third-party, 2023 and macOS 13, so `{confidence: practitioner, pre-macOS 26}`.
- Command: `sudo fdesetup authrestart -delayminutes 0` (or `-inputplist` to pass credentials non-interactively), which runs as root and "itself prompts for a password to unlock the FileVault root volume" [hma-reboot-man-fdesetup-authrestart]{1}[hma-reboot-man-fdesetup-authrestart]{4}; the practitioner article adds that a FileVault-entitled user's short name and password are required [hma-reboot-eclectic-authrestart]{2}.
- `softwareupdate` has Apple-silicon-specific credential flags: `--stdinpass` ("Collect a password from stdin without interaction. Apple silicon only.") and `--user` ("An owner user to authorize installation. Apple silicon only.") [hma-reboot-man-softwareupdate]{4}[hma-reboot-man-softwareupdate]{5}. The man page does not say these arrange an authenticated (unlock-skipping) restart; they authorise the install. `{inferred: --stdinpass plus --restart may land at the login window after the update, because the page ties neither flag to key retention.}` Treat `fdesetup authrestart` as the unlock-skip path documented in the fetched sources.
- What protection is reduced: `fdesetup` "deliberately stores at least one additional copy of a permanent FDE (full disk encryption) unlock key in both system memory and (on supported systems) the System Management Controller (SMC)", and the key is removed after a successful unlock [hma-host-man-fdesetup]{2}[hma-host-man-fdesetup]{3}. `pmset destroyfvkeyonstandby` prevents saving the key across standby modes [hma-host-man-fdesetup]{2}, a setting the pmset page describes as destroying the key when going to standby, with the user then prompted for the password coming out of standby [hma-host-man-pmset]{5}.
- Scope limit `{inferred: a key held in memory or SMC for a pending restart cannot cover an unplanned power loss, a UPS-initiated shutdown, or a kernel panic, because those paths do not run the authenticated shutdown; the man page describes authrestart as launching shutdown(8) after authentication [hma-host-man-fdesetup]{3}}`. The practitioner article records a case where an update's authenticated restart "didn't work properly" and the Mac stopped at a password prompt [hma-reboot-eclectic-authrestart]{4}.
- After an authrestart, `{inferred: the Mac boots to the login window with FileVault already unlocked and no GUI user logged in}`: updates "log the current user back in automatically" through a mechanism "not made available to mere users" [hma-reboot-eclectic-authrestart]{3}, and automatic login is unavailable with FileVault on [hma-host-apple-autologin]{1}. Daemons such as `tailscaled` and sshd then run (see section 3); GUI-domain LaunchAgents do not.
- Alternative for the unplanned-reboot case: macOS 26 Apple silicon "FileVault can be unlocked over SSH after a restart if Remote Login is turned on and a network connection is available" [hma-host-apple-security-filevault-managing]{1}; one practitioner reports this works over Ethernet and, from macOS 26.5, Wi-Fi, with an administrator password [hma-host-geerling-filevault-ssh]{1}[hma-host-geerling-filevault-ssh]{3}[hma-host-geerling-filevault-ssh]{4}. `tailscaled` as a LaunchDaemon runs at boot "before any user has logged in" [hma-host-tailscale-tailscaled-wiki]{3}, but whether it runs before the FileVault unlock is not established; the pre-boot SSH path is LAN-reachable only `{inferred}`.

## 3. FileVault off on Apple silicon: exposure

What the platform provides with FileVault off:

- All Apple-silicon FileVault key handling occurs in the Secure Enclave and keys are "never directly exposed to the CPU" [hma-reboot-apple-security-filevault-volume]{1}. All volumes are created with a volume encryption key [hma-reboot-apple-security-filevault-volume]{1}. With FileVault on, the wrapping key is "protected by a combination of the user's password and hardware UID" [hma-reboot-apple-security-filevault-volume]{2}. With FileVault off from Setup Assistant, "the volume is still encrypted but the volume encryption key is protected only by the hardware UID in the Secure Enclave" [hma-reboot-apple-security-filevault-volume]{3}.
- What FileVault adds is a credential at boot: "their credentials are required during the boot process" [hma-reboot-apple-security-filevault-volume]{6}; Apple's user guide states it keeps someone "from decrypting or getting access to your data without entering your login password" [hma-host-apple-macos-fv-help]{1}. A trade-press summary says it "prevents unauthorized access to data on the drive even if someone has physical access" [hma-host-tidbits-filevault-default]{4}.
- Consequence, composed: `{inferred: with FileVault off the Secure Enclave can release the volume key at every boot without any user secret, so the Data volume is available to macOS before and without login; a stolen SSD moved to another computer stays unreadable because the key is bound to that SoC's UID, but the Mac as a whole is protected only by its account passwords and what recoveryOS permits}`. The Apple page states the removed-device property explicitly only for FileVault on [hma-reboot-apple-security-filevault-volume]{5}; the FileVault-off removed-device case is inference from the UID binding.

What a person with the machine can do (stated precisely, with gaps):

- Enter recoveryOS: press and hold the power button from a shutdown state; double-press and hold for fallback recoveryOS [hma-reboot-apple-security-boot-modes]{1}. Apple frames recoveryOS entry as a human-with-physical-access signal and says Apple-silicon Macs "won't require (or support) a firmware password" because critical changes are gated by user authorization [hma-reboot-apple-security-startup-policy]{1}. Lowering startup security needs recoveryOS plus administrator credentials: a holder of an administrator name and password "can always choose the security policy" [hma-reboot-apple-security-startup-policy]{3}.
- Password reset in recoveryOS: "Forgot all passwords?" flows ask for the Apple Account used with the Mac or, where FileVault is on, a recovery key, and Terminal `resetpassword` is available from Recovery [hma-reboot-apple-forgot-password]{1}[hma-reboot-apple-forgot-password]{2}. Apple's page does not say what these flows require when FileVault is off or whether an unauthenticated person can reset an account password. `{ambiguous: no fetched Apple text states what recoveryOS grants a person without credentials against a FileVault-off Data volume. The conservative reading is that recoveryOS and password-reset paths exist and are the barrier; Apple has not attested their strength for this case.}`
- Erase and reuse is blocked by Activation Lock if Find My is on: "Your Apple Account password or device passcode is required before anyone can turn off Find My, erase your Mac, or reactivate and use your Mac" [hma-reboot-apple-actlock-mac-support]{1}. On Apple silicon it needs Full Security (default) and two-factor Apple Account [hma-reboot-apple-actlock-mac-support]{3}, and works through LLB, LocalPolicy and an activation certificate [hma-reboot-apple-security-activation-lock]{3}[hma-reboot-apple-security-activation-lock]{5}. Activation Lock deters reactivation after erase; it is not a data-at-rest control. `{inferred: it adds no confidentiality for a Mac that still boots macOS normally.}`
- Lost Mode: locks the device with a passcode, must be set up before loss, and starts "when it goes online" [hma-reboot-apple-findmy-lostmode]{1}[hma-reboot-apple-findmy-lostmode]{2}[hma-reboot-apple-findmy-lostmode]{4}. `{ambiguous: Apple does not say whether Lost Mode interacts with FileVault state.}`
- Full Security (default) personalises the macOS signature to the Mac's ECID [hma-reboot-apple-security-startup-policy]{2}, so booting older vulnerable macOS images is constrained; this does not bear on data access to the installed OS.

What changes after a boot with no login when FileVault is off versus on:

- `{inferred}` With FileVault off there is no pre-boot unlock, so the system boots to the login window with the Data volume available; sshd and system LaunchDaemons start, as the daemon boot model says: launchd loads daemons from `/Library/LaunchDaemons/` after boot, and "a daemon should not care whether a user is logged in" [hma-host-apple-launchd-archive]{1}[hma-host-apple-launchd-archive]{4}. The tailscaled LaunchDaemon "can run at system boot before any user has logged in" [hma-host-tailscale-tailscaled-wiki]{3}; the Tailscale KB says unattended mode is Windows only and the macOS client runs in the user login session [hma-host-tailscale-run-unattended]{1}[hma-host-tailscale-run-unattended]{3}, a tension recorded in section Contradictions.
- With FileVault on, "their credentials are required during the boot process" [hma-reboot-apple-security-filevault-volume]{6}, so after a power loss the Mac waits at the unlock screen unless SSH unlock or physical entry occurs.
- With FileVault off, automatic login becomes available `{inferred}`, since Apple lists FileVault being on as a condition that makes manual login required [hma-host-apple-autologin]{1}. That would give the agent user a GUI session after reboot, which matters for Herdr (section 5). The effect of automatic login on the login keychain was not established and is not claimed.
- Secrets on a FileVault-off host sit unencrypted from the user's perspective: Claude Code falls back to `~/.claude/.credentials.json` mode 0600 when the Keychain rejects a write [hma-host-claude-code-auth]{1}, and Codex can store `~/.codex/auth.json` in plaintext [hma-host-codex-auth]{2}. `{inferred: these files are readable by whoever can log in as that user.}`

Net exposure statement: FileVault off converts the physical-possession threat from "needs a password to decrypt" to "needs an account password or a recoveryOS path"; the first barrier is stated by Apple, the second barrier's strength is not.

## 4. UPS on macOS

- Built in: System Settings > Energy > UPS Options on a desktop Mac, for UPS devices "connect[ed] to the computer's USB port"; options choose when to shut down after power failure and a slider sets a time or battery level; with several options the Mac shuts down "when the first condition is met" [hma-reboot-apple-ups-help]{2}[hma-reboot-apple-ups-help]{3}[hma-reboot-apple-ups-help]{4}. Some UPS devices simply run until their batteries are exhausted and then shut down [hma-reboot-apple-ups-help]{2}.
- CLI: `sudo pmset -u haltlevel <percent> haltafter <minutes> haltremain <minutes>`; `-1` turns a setting off, and the system halts on the first condition [hma-reboot-man-pmset-ups]{1}. `pmset -g ups` shows thresholds and `pmset -g ps` shows batteries and UPSs [hma-reboot-man-pmset-ups]{2}[hma-host-man-pmset]{8}. Example from the man page: `pmset -u haltlevel 25 haltremain 30` [hma-reboot-man-pmset-ups]{3}. Settings apply only to "desktop and server" [hma-reboot-man-pmset-ups]{4}; root is required [hma-reboot-man-pmset-ups]{5}. A pattern to leave margin for a Herdr save and agent shutdown is `extends`; no source gives a margin.
- How the shutdown is carried out (local read, operator laptop, not the mini): the `ioupsd` launchd job matches HID devices on usage pages 132 and 133 [hma-reboot-local-ups-plumbing]{2}, and the `upsshutdown` script runs `shutdown -h now` under the comment "Gently shutdown the system immediately" or `shutdown -hu now` under "Wait for UPS to take the system down abruptly and unexpectedly" [hma-reboot-local-ups-plumbing]{1}. `shutdown(8)` without `-o` is the "nicely notify users" path that signals launchd [hma-reboot-local-ups-plumbing]{3}. `{inferred: a UPS emergency stop is a normal launchd shutdown, so processes receive termination signals; Apple's UPS page does not say apps are notified, and which script path the Energy settings take was not observed.}`
- Herdr behaviour across a graceful macOS restart or shutdown: v0.9.4 states "Herdr saves before the system starts closing apps, so agents come back where they were" for a Mac restart [hma-herdr-releases]{3}. The Herdr docs document the shutdown-delay save only for Linux systemd-logind and say it "does not cover forced shutdown, power loss" [hma-herdr-tui-session-state-docs]{4}. Pre-0.9.4 reports show macOS terminating Pi and OMP agents at logout before Herdr saved, so those panes came back as shells [hma-reboot-herdr-issue-4414]{1}[hma-reboot-herdr-issue-4414]{2}; fixed for graceful TERM/HUP in v0.9.4, while "a hard kill that cannot run the native shutdown hook remains outside this path" [hma-reboot-herdr-issue-4414]{4}. `{inferred: a UPS-initiated shutdown behaves like the restart case; no fetched source tests Herdr under a UPS shutdown.}`
- Restart when power returns: Apple's "Start up when power is connected" = Always makes the Mac "automatically turn on when power is restored after a power failure", on a Mac mini introduced in 2024 or later and macOS 26.5 or later; wait about 30 seconds between disconnecting and reconnecting power [hma-host-apple-poweron-mini]{1}[hma-host-apple-poweron-mini]{2}[hma-host-apple-poweron-mini]{3}[hma-host-apple-poweron-mini]{4}. The pmset keys are `autorestart` (power loss) and `autorestartatconnect` (power connect) [hma-host-man-pmset]{3}. `{inferred: after a UPS-initiated shutdown the Mac turns on again only if the UPS output (or mains to the Mac) is actually cut and restored; a UPS that keeps powering the Mac after the OS has halted gives the Mac no power event. Test this with the specific UPS.}`
- With FileVault on, a power-restore start lands at the credentials prompt `{inferred, from [hma-reboot-apple-security-filevault-volume]{6}}`, so a UPS improves clean shutdown but not unattended recovery unless SSH unlock or FileVault-off is also used.
- No Apple article beyond the UPS Options page was found for UPS support; supported-UPS definition is absent from the man page [hma-reboot-man-pmset-ups]{3}.

## 5. Herdr boot start and resume without a human

- Documented server form: `herdr server` "runs the headless server explicitly. Use it for supervised or service-style setups" [hma-herdr-tui-remote-docs]{14}. The fetched Herdr docs contain no launchd plist, systemd unit or boot-start instruction [hma-reboot-herdr-docs-named-sessions-handoff]{1} (see its structural notes). Named sessions give independent servers with their own sockets and state: `herdr session list|attach|stop|delete`, and `herdr --remote <host> --session <name>` [hma-reboot-herdr-docs-named-sessions-handoff]{1}[hma-reboot-herdr-docs-named-sessions-handoff]{3}. A search of herdrdev/herdr issues for reboot, autostart, login item and boot returned no issue titled for boot-time auto-start (search listing, 2026-11-10).
- Evidence that a launchd-run `herdr server` works: issue #4926 reports a LaunchAgent with `RunAtLoad` and `KeepAlive = { SuccessfulExit = false; }`; the server froze restoring a `session.json` because macOS blocked `~/Documents` under launchd, workaround "allow herdr in privacy & security > files and folders", responsiveness fixed in v0.9.4 [hma-reboot-herdr-issue-4926]{1}[hma-reboot-herdr-issue-4926]{2}[hma-reboot-herdr-issue-4926]{3}. A grant made in System Settings is a GUI action.
- The login-context problem is the main risk on this host. Panes inherit the server's launchd context; a server started over SSH or as a background job may lack Keychain access [hma-herdr-tui-troubleshooting-docs]{1}, panes then report `launchctl managername` = `Background` [hma-reboot-herdr-issue-966]{1}; the maintainer's fix is a GUI terminal or a per-user LaunchAgent in `gui/$UID` [hma-reboot-herdr-issue-966]{3}. Herdr's own automatic start on macOS submits a one-shot job to `gui/<uid>` but falls back to a direct spawn when `SSH_CONNECTION` is set [hma-reboot-herdr-source-launchd-spawn]{2}[hma-reboot-herdr-pr-5236]{2}[hma-reboot-herdr-pr-5236]{3} (the PR is merged on master, not in v0.9.5 per [hma-herdr-releases]{6}). A LaunchAgent loads only when a user logs in [hma-host-apple-launchd-archive]{2}; with FileVault on and no automatic login there is no GUI user after a reboot. A LaunchDaemon can set `UserName` but only in the system domain, which has "no distinct sessions" [hma-reboot-man-launchd-plist]{1}[hma-reboot-man-launchd-plist]{2}. `{inferred: on the seed host every server start after a reboot is either an SSH-context direct spawn or a system-domain daemon, i.e. the Background context, so Keychain-backed tools fail inside panes.}` Mitigation for agents: Claude Code stores credentials in `~/.claude/.credentials.json` when the Keychain rejects the write [hma-host-claude-code-auth]{1}, and Codex has a file or auto store [hma-host-codex-auth]{2}; other Keychain-backed CLIs would fail [hma-reboot-herdr-issue-966]{1}. `{inferred}` The FileVault-off plus automatic-login variant (section 3) is the configuration that creates a `gui/<uid>` domain after reboot; it was not tested by any fetched source.
- Start race: a peer's saved-machine `remote-client-bridge` starts a server whenever none is listening, including right after a reboot, "SSH comes up before GUI login, so the bridge usually wins", producing a Background-context server whose panes cannot read the login keychain; open, no maintainer fix [hma-reboot-herdr-issue-4291]{1}[hma-reboot-herdr-issue-4291]{4}[hma-reboot-herdr-issue-4291]{5}[hma-reboot-herdr-issue-4291]{6}[hma-reboot-herdr-issue-4291]{7}. On a host used only from a Moshi/SSH phone client, the equivalent is that the first `herdr` run after reboot starts the server in the SSH context `{inferred, from [hma-reboot-herdr-pr-5236]{3}}`.
- Resume without an interactive client: after a server stop and start, Herdr restores layout and relaunches agents with native resume commands only for panes whose agents reported a session through a current official integration [hma-herdr-tui-session-state-docs]{1}[hma-herdr-tui-session-state-docs]{3}[hma-herdr-tui-session-state-docs]{5}; `[session] resume_agents_on_restore` is enabled by default and "After a client attaches and provides terminal size and theme context, Herdr resumes eligible restored agent panes across workspaces and tabs without waiting for each pane to be focused" [hma-lead-herdr-tui-state-api]{7}. Master source agrees: resume is attempted on the foreground-client resize path and requires a host terminal theme unless a 750 ms wait elapses [hma-reboot-herdr-source-resume-gating]{1}[hma-reboot-herdr-source-resume-gating]{2}[hma-reboot-herdr-source-resume-gating]{3}. `{inferred: with no client attached after a reboot, restored panes are layout plus shells and agents do not resume until a client attaches}`; the headless server uses a 120x40 virtual terminal only for layout and new panes (`headless_cols`, `headless_rows`) [hma-herdr-tui-remote-docs]{13}, and no config key, flag or issue found starts agents with no client. A scripted client is `{contested: not established}`: the docs describe `herdr terminal session control <id> --takeover --cols 120 --rows 40` as a writable controller and `session observe` for read-only observers [hma-herdr-tui-remote-docs]{11}, but whether either counts as the client that triggers resume was not traced (see the structural notes of hma-reboot-herdr-source-resume-gating). Test it on the host: reboot, attach a scripted client, check `herdr agent list`.
- Failure modes of resume: open p1 issues for wrong Codex or Claude session identity and OpenCode restore [hma-herdr-open-issues]{9}; v0.9.5 reverted Codex turn hooks so Codex state is screen-derived [hma-herdr-releases]{2}. Layout snapshots: up to 48 kept, at most one per 15 minutes; writes are crash-safe since v0.9.4 [hma-herdr-tui-session-state-docs]{4}[hma-herdr-releases]{3}.
- `herdr update --handoff`: experimental, opt-in; replaces a running server and keeps pane processes alive, while "in-flight CLI or API requests, waits, subscription streams, client sockets, and pane-to-pane messages may be interrupted" [hma-reboot-herdr-docs-named-sessions-handoff]{4}. Limits: only Herdr-updater installs, not Homebrew, mise or Nix [hma-reboot-herdr-docs-named-sessions-handoff]{6}; more than 64 panes need a sending server that already has batching, else a normal restart that ends pane processes [hma-reboot-herdr-docs-named-sessions-handoff]{5}. Open issues: macOS handoff clears one pane's `agent_session` when two panes share an id (#5443) [hma-reboot-herdr-issues-handoff]{1}; handoff server loses responsible-process attribution on macOS (#808), affecting TCC-gated access and 1Password prompts [hma-reboot-herdr-issues-handoff]{2}; scrollback lost across a version jump (#3864) [hma-reboot-herdr-issues-handoff]{3}; handoff under a supervising service manager killed or orphaned supervision on Linux systemd (#4972) [hma-reboot-herdr-issues-handoff]{4}. Handoff preserves the source server's service context and cannot fix an older server's inherited context [hma-herdr-tui-troubleshooting-docs]{3}. Handoff does not help across a reboot (processes are gone). Recommendation: do not use handoff for routine updates on a supervised host; stop the server deliberately and let native resume rebuild. `extends`, from the issue evidence and the "experimental" label [hma-reboot-herdr-docs-named-sessions-handoff]{4}.

## Recommended configuration (composed)

1. Updates: install-macOS-updates off, BSI automatic install off, a monthly manual window, `softwareupdate --install --os-only --restart` after `herdr server stop`; accept slower patches.
2. Planned reboots: `sudo fdesetup authrestart -delayminutes 0`; unplanned reboots: pre-boot SSH unlock or FileVault-off decision by the operator.
3. UPS: USB UPS plus `pmset -u haltlevel/haltremain`, "Start up when power is connected" = Always, and a physical test of power-return behaviour.
4. Herdr: accept that post-reboot recovery needs one attach (Moshi) to resume agents; keep `resume_agents_on_restore` default; use named sessions; avoid `--handoff`; check Keychain context with `launchctl managername`.

## Disconfirming analysis

- Update control: searched for a CLI or documented non-MDM way to defer updates; the man page has no disable verb [hma-reboot-man-softwareupdate]{8}, and deferral pages are device-management pages [hma-reboot-apple-deploy-enforce-updates]{1}. No disconfirming source (a personal deferral) was found; absence is `{confidence: absence-of-evidence}`.
- BSI: searched for a statement that BSI never forces a restart; found the opposite [hma-reboot-apple-bsi-platform-support]{1}. Searched for a statement that BSI cannot be disabled; found the user switch [hma-reboot-apple-bsi-support]{3}.
- authrestart: searched for Apple text saying it is unsupported on Apple silicon; none found, and `supportsauthrestart` returned true on one Apple-silicon Mac [hma-reboot-local-softwareupdate-state]{3}. Searched for Apple text confirming support on the Mac mini or macOS 26; none found.
- FileVault off: searched for an Apple statement that recoveryOS exposes the Data volume without credentials, or that it does not; neither found. The Apple FileVault page states the FileVault-off key binding [hma-reboot-apple-security-filevault-volume]{3}, which supports the exposure claim; Apple's startup policy page says critical changes are gated by user authorization [hma-reboot-apple-security-startup-policy]{1}, which weakly disconfirms a broad "attacker can do anything in recoveryOS" claim for security downgrades but not for data access.
- UPS: searched Apple text for graceful application handling and for restart on power return after a UPS shutdown; Apple states the second only for power restoration generally [hma-host-apple-poweron-mini]{3}. Graceful behaviour rests on a local script on a different Mac model.
- Herdr: searched for a boot-start document, config key or issue; none. Searched for evidence that agents resume headlessly; docs and source both condition on a client [hma-lead-herdr-tui-state-api]{7}[hma-reboot-herdr-source-resume-gating]{3}. Searched for evidence that the SSH-context Background problem is solved for SSH starts: PR #5236 explicitly keeps the direct spawn over SSH [hma-reboot-herdr-pr-5236]{3}.

## Contradictions

- **Tailscale before login on macOS.** The Tailscale KB says "Running it as a standalone system daemon is not currently supported" on macOS and unattended mode is Windows only [hma-host-tailscale-run-unattended]{1}[hma-host-tailscale-run-unattended]{3}; the Tailscale wiki on the open-source `tailscaled` says it "can run at system boot before any user has logged in" [hma-host-tailscale-tailscaled-wiki]{3}, and the variants table marks "Run before login" yes for `tailscaled` only [hma-host-tailscale-macos-variants]{3}. Positions stand side by side; relationship `qualifies` (the KB statement does not name a variant).
- **Rapid Security Responses versus Background Security Improvements.** The Mac User Guide still names Rapid Security Responses [hma-reboot-apple-macos-autoupdates]{1}; the Support and Platform Support articles describe Background Security Improvements for 26.1 and later [hma-reboot-apple-bsi-support]{1}[hma-reboot-apple-bsi-platform-support]{3}. `tension`; not reconciled.
- **Herdr automatic start.** Docs say automatically started macOS servers use a per-user service context so logout does not kill panes' macOS services [hma-herdr-tui-troubleshooting-docs]{2}; PR #5236 says SSH starts keep the direct spawn [hma-reboot-herdr-pr-5236]{3} and issue #4291 reports SSH-context servers that lose Keychain access [hma-reboot-herdr-issue-4291]{4}. `qualifies`: the docs sentence is about automatic (non-SSH) starts.
- **Herdr handoff stability.** Docs call handoff experimental [hma-reboot-herdr-docs-named-sessions-handoff]{4}; a Linux reporter finds the handoff step itself works [hma-reboot-herdr-issues-handoff]{4}, other reporters find session-state loss [hma-reboot-herdr-issues-handoff]{1}[hma-reboot-herdr-issues-handoff]{3}. `tension`.

## Revisit if

- Apple documents authenticated restart on Apple silicon or macOS 26 `softwareupdate` behaviour for FileVault Macs, or `fdesetup supportsauthrestart` returns false on the Mac mini.
- Apple publishes a non-MDM deferral control, or Background Security Improvements change restart behaviour.
- Apple states what recoveryOS grants without credentials when FileVault is off.
- A UPS test on the actual Mac mini and UPS shows non-graceful shutdown or no power-return start.
- Herdr ships a documented launchd/boot-start unit, a resume-without-client option, merges #5236 into a stable tag, or resolves #4291, #5443 or #808.
- The operator changes the FileVault or automatic-login posture.
